_Brand Visual Guide module (`feature/brand-visual-guide`, 5 commits, migrations 0094-0095, **not yet merged to `main`**, 16 August 2026):_
- **What it is.** A new per-client library inside the portal: three sibling categories (Guidelines, Assets, Templates), each a flat list of items grouped for display by a fixed `group_label` set per category. Admin gets full CRUD, drag reorder within a group, inline status/visibility toggles, and preview-as-client/preview-as-public. Client gets a read-only view of published items visible to them plus a note field. Public gets a clean, chrome-free view of published-and-public items via a per-client share link.
- **Built from a PRD (v2 + v3 delta) and a working no-backend React prototype**, neither of which is committed to this repo — both were supplied as attachments and read in full before any code was written, per the standing instruction to read the referenced docs before starting. The prototype's own hardcoded Newgen demo art (a hand-drawn Crown Pillar mark, a generated kolam SVG tile) was deliberately **not** ported: in the real app a logo mark or pattern is just an uploaded image file like any other, rendered through `ProgressiveImage`, not redrawn from scratch. Its `BrandSwitcher` and three-way `RoleSwitcher` were review aids only and were not built at all — see the ClientPanel decision below for why no switcher is needed.
- **Two architecture questions the brief flagged as open were resolved with the user before writing code, not assumed.** (1) Where the admin surface attaches: `ClientPanel.tsx` (`src/portal/admin/ClientPanel.tsx`) is the real per-client admin panel, opened from a `ClientsList` row and scoped to one `clientId` for its lifetime — it already does the scoping the prototype's `BrandSwitcher` was standing in for, so **no switcher was built**. But "the same relationship Outputs has to ProjectPanel" meant something structural: `ClientPanel` was flat sections (Client info, Proposals, Invoices, Projects, Danger zone), not tabbed, unlike `ProjectPanel`. Restructured into a `TabBar`/`TabFadeIn` layout (Info/Proposals/Invoices/Projects/Brand Visual Guide) to match; Danger zone folded into the Info tab. (2) Where the client route lives: `ClientNav` has exactly 6 top-level tabs, deliberately sized for the mobile bottom bar (PR #13). Decision: add a 7th (`/portal/brand`, `Palette` icon) rather than nest it under an existing tab — `tabLabel` gained `overflow:hidden`/`textOverflow:ellipsis`/`whiteSpace:nowrap` so 7 tabs stay legible at narrow widths (Dashboard/Proposals/Campaigns are the widest labels) instead of wrapping or overflowing; `tab { flex: 1 }` already redistributes width with no other change needed.
- **A third architecture gap surfaced only once the public route was actually being built, not anticipated by the brief's DATA MODEL section.** The spec's `get-brand-visual-file-url` edge function is modelled on `get-output-file-url`, which is a **per-file** share link — Outputs' public page shows exactly one file, given by its own token. But the Brand Visual Guide public page browses a **whole client's** published library across three category tabs, and nothing in the stated schema gives a stable, non-guessable identifier for "which client" to put in that URL — `clients` had no public-facing token at all. Resolved with the user: added `clients.public_token` (migration 0094), matching the convention every other public surface in this app already uses (invoices, proposals, outputs — one opaque token per thing, never a raw id), and a new anon-callable listing RPC, `get_brand_visual_items_by_client_token` (migration 0095, SECURITY DEFINER, filters to `status='published' AND visibility='public'` server-side, mirrors `get_invoice_by_token`'s shape). The per-file edge function still exists and still matters — it mints the actual signed download/preview URL once an item is opened — but it is not what makes the browsing page work.
- **RLS mirrors `mockup_sets`/`project_output_files`, not invented fresh.** Admin: `is_admin()` SECURITY DEFINER only, no inline subquery. Client: `client_id in (select id from clients where profile_id = auth.uid()) and status = 'published' and visibility in ('client','public')`. **No anonymous SELECT policy on the table at all** — public access goes entirely through the token-gated RPC and edge function, both service-role/SECURITY DEFINER, same reasoning already on record for Outputs (a Postgres RPC can't mint a Storage signed URL, so the edge function is needed regardless of the RLS shape).
- **Storage bucket `brand-visual-files` (private, 50MB limit, no MIME allow-list — matches `project-outputs`, the closest analog given the same spread of file types: SVG/PDF/AI/DOCX/MP3/MP4) was verified to actually exist via a direct `storage.buckets` query immediately after applying the migration**, before any UI work touched it — the stage-attachments bucket-never-created bug (PR #12) is exactly the failure mode this check exists to catch. Path stays flat, `{client_id}/{random_id}_{filename}`, so moving an item between groups or categories is a plain `client_id`-scoped `UPDATE`, never a storage rename or copy — same lesson as `project-outputs`.
- **Downloads are real, not a "not wired up" toast.** Admin/client resolve signed URLs directly (`resolveAuthenticatedFileUrls` in `utils/brandVisual.ts`), storage RLS already telling the two apart; the public route goes through `get-brand-visual-file-url`. Both paths return two separate signed URLs, never one reused for both — the download link needs `Content-Disposition: attachment` (Storage's `download` option), but applying that header to the same URL an image/video preview uses risks the preview trying to download instead of render, the same reasoning already documented for `get-output-file-url`.
- **Preview mode reuses the real view components, not a third copy.** `BrandVisualClientView` and `BrandVisualPublicView` (`src/portal/components/shared/`) take their item list as a prop and never fetch anything themselves — the real client route (`BrandVisualPage.tsx`) supplies RLS-scoped live data, the real public route (`PublicBrandPage.tsx`) supplies the RPC's data, and admin's two preview buttons supply the admin's own already-loaded full item list, client-side filtered to `status='published'` plus the target audience's visibility (`filterForPreviewAudience`). One component, three call sites, same pattern already established for `InvoiceDocument`. Draft items are therefore invisible in preview automatically, with no special-case code — filtering happens once, before the component ever sees the data. Exiting preview returns to the same category/group because the underlying nav state was never touched by entering it; only the previewed component's *own* internal nav state resets, and that state is thrown away when the preview branch unmounts.
- **The note field is a deliberate, explicitly-labelled stub, not a silent no-op.** Nothing in the stated data model backs a per-client note (no table, no column), and adding one wasn't in scope for this pass. Rather than accept input that would vanish on refresh, the textarea renders `disabled` with an inline "Not wired up yet" caption. Flagged here rather than fixed quietly so a future pass knows exactly what's missing and why.
- **Admin add/edit form matches the PRD's stated field list exactly** (document/image/video/audio/link, with a real file upload for all four non-link types) and does **not** add swatch/specimen/section editors — the PRD's own Section 4 field list never mentions them; those three layouts exist in the renderer for seed/manually-inserted content, and the edit form preserves whatever structured `detail` an item already has rather than clobbering it on save.

_Cron business-hours gate, timezone-starvation fix, and three supporting fixes (5 commits `6365b135`..`bc364c5d` direct on `main`, no migrations, **pushed to origin**; `send-confirmed-outreach-touches` deployed **v14 at 2026-08-11 18:56:30Z**, 11-12 Aug 2026):_
- **Root cause: `capped++` silently invalidated the precondition the cron's whole design rested on.** `send-confirmed-outreach-touches` was deliberately built as a dumb executor — it trusted `scheduled_for` completely and never re-checked business hours, which was correct *only* under an unstated assumption: that `scheduled_for` is always a freshly-computed, business-hours-valid instant that comes due once and is consumed immediately. The daily cap breaks it. A touch that loses its slot is only `capped++` — **nothing is written** — so its `scheduled_for` stays in the past indefinitely and `.lte(scheduled_for, now)` matches on every subsequent tick forever. The row then ships at whatever arbitrary moment a cap slot next frees. The contract was never violated by the cron; a second mechanism quietly made the stored value meaningless. Worth keeping that distinction: this was not "the cron forgot to check."
- **The incident it caused.** 25 US touches went out at **20:00 America/New_York** on 10 Aug — 150 minutes past the 17:30 close, 25 of 25 outside the window, verified per-row against each lead's resolved timezone. Mechanism: the cap counter resets on the **UTC** day boundary (`new Date().toISOString().slice(0,10)`), and 00:00 UTC *is* 20:00 EDT. So the reset instant is itself outside every US recipient's window, and the backlog fired into it.
- **Fix 1 — business-hours gate at tick time (`6365b135`).** The cron now calls `computeSendDecision` from the same `_shared/businessHours.ts` the two click paths use, making it the module's **third** consumer. Deliberately **stateless**: `scheduled_for` is never rewritten and `decision.scheduledFor` is discarded. An out-of-window row is skipped, no write, no cap slot consumed, reconsidered next tick. The alternative — recompute and persist a new hold — was rejected because it puts mutation of that column back into the one function that has already corrupted it once (see the PR #19 entry below), and loses the approval-time target without a new column. Placed after the cancel guards so suppressed/malformed rows are still cleaned out at any hour, and before any render or Resend call. `recipient_timezone` and `leads.country` added to the select — neither was fetched before.
- **Fix 2 — deterministic, fair ordering (`c63df041`).** The eligible query sorted on `scheduled_for` alone, but that column is **not a discriminator**: `computeSendDecision` hands a whole day's approvals one identical instant, and **44 of 44 eligible rows tied on it** when measured. Postgres was free to return them in any order, so the subset fitting inside `BATCH_LIMIT` was arbitrary tick to tick — and once Fix 1 landed, out-of-window rows still occupy batch slots, turning that arbitrariness into a starvation risk against minority timezones. Now orders `scheduled_for`, then `draft_confirmed_at` ASC, then `id` ASC. `draft_confirmed_at` was chosen over `created_at` (which `enroll_lead` stamps on every step of an enrollment at once, so it barely varies across a batch) and over `id` alone (a random uuid — deterministic but arbitrary, no fairness property); it is already on the row, guaranteed non-null by the query's own `.not(...)` filter, and drains FIFO by when a human actually approved. `id` is the final key purely for determinism, since a bulk approve can land two rows in one millisecond. `BATCH_LIMIT` 50 → 200: the batch is a *candidate* list, not a send list — at most `DAILY_CAP` (25) rows reach Resend and the loop short-circuits on its first line once the cap is spent, so the added cost is one `suppression_list` lookup per candidate on ticks where cap remains.
- **This reduces starvation, it does not eliminate it — logged as an open item in Section 11.** Ordering is timezone-blind. Above ~200 eligible rows with mixed geography a single timezone can still fill the batch and hide an in-window row behind it.
- **Fix 3 — honest display for deferred touches (`f2f9bc4e`).** Statelessness has a UI cost: a declined row keeps a past `scheduled_for`, and `TouchProgressLine` read past-due as "Queued — sending shortly" in gold, so a row waiting since yesterday claimed it was seconds from sending. Three states now — future hold names its time; past-due under 15 minutes is genuinely queued behind the next tick; anything older reads **"Waiting for next available window"** in muted. 15 minutes is three cron ticks, so a slow tick or clock skew cannot mislabel a real send. **Display only** — derived from `draft_confirmed_at` and `scheduled_for`, both already present. No column, no migration, no query change, same props. Fixes TodayTab's Scheduled section and ActivityTab's table and mobile card at once, since all three render through this one component.
- **Fix 4 — ActivityTab TIME column shows date *and* time (`93cc57b8`).** `formatPortalDate` returns the clock time only for rows dated today and a bare day/month otherwise, so every row of a batch read `11 Aug` and a 20:00-local send was indistinguishable from a compliant one without querying the database — exactly the check Fix 1 needs to be verifiable from the UI. **Searched before writing:** `src/portal/utils/` has exactly one date formatter; every other timestamp display in the portal is module-private (`TouchProgressLine`'s `formatStepTime`, `TodayTab`'s `formatPendingDate`) or inline at the call site (the approve toasts, `OutreachSendModal`'s deferral notice) — all recipient-timezone scheduler displays, none exported, none reusable. Genuine gap, so **`formatPortalDateTime` was added as a sibling inside `formatDate.ts`**, not a new file and not a call-site wrapper: it shares `istDateParts` and the single `IST_TIME_ZONE` constant, keeps the `'-'` contract for null/unparseable, and keeps the relative-year rule. One module still owns portal timestamp rendering. Stays on **IST**, the convention this column and the engagement tooltips beside it already use; recipient-local is ActivityTab's *other* convention and belongs to its scheduler displays — putting it in the TIME column would make rows in different zones incomparable as a chronological axis.
- **Fix 5 — every edge function error message was unreachable from the UI (`bc364c5d`).** On a non-2xx, `functions-js` throws `new FunctionsHttpError(response)` and returns it as `error` with `data: null`, **never parsing the body** — the JSON decode at `FunctionsClient.js:275` sits *after* the throw at `:271`. So the ubiquitous `if (data?.error)` check cannot fire for a real server-side failure. Since every guard in `send-outreach-email` returns non-2xx, all seven of its specific messages were dead code and every failure surfaced as "Something went wrong. Please try again." — including `daily_cap_reached`, which was the error actually being hit. New shared `src/portal/utils/invokeError.ts`: `invokeErrorCode(data, error)` recovers the code from `error.context` (the documented path), clones the Response so a second read can't hit a consumed stream, and falls back to `network_error` on a non-JSON body; `humanizeErrorCode(code, fallback)` serves call sites with a free-text slot but no message map, returning the caller's own wording for `network_error`/null so it can never make an existing message vaguer. Applied to **all six** invoke sites. The server-side alternative (return 200 with an error field, needing no client change) was rejected: `fail()` is shared with `not_authenticated`/`not_allowed`/`method_not_allowed`, so it would hand back success codes for auth failures, and it inverts a convention the codebase already relies on — the `already_approved` HTTP 400 documented in the PR #21 entry below.
- **Newly reachable UI branches verified, not assumed.** In `OutreachSendModal`: `daily_cap_reached` now reaches its dedicated capped panel and disables the send button via `canSendEmail`; `missing_observation` opens the inline observation editor; `unresolved_variables` stays excluded from the generic banner; unknown codes fall through `emailErrorMessage`'s `?? fallback`. The two sites whose error UI is a fixed enum (`LeadDrawer`'s `scoringState`, `AddLeadModal`'s `extractBanner`) keep their banner and log the code rather than dropping it.
- **Verification.** `tsc --noEmit` at **36 errors, exactly the documented baseline**, none in any touched file; `npm run build` clean. The edge function is **not** typechecked — Deno is not installed locally, so the cron change is verified by reading only. The gate has **not** yet been watched declining a real send at a real closed window; the next out-of-window tick is the first live proof.
- **Also on `main` from the same session, one commit earlier (`2e9e173a`, deployed `send-outreach-email` v21 / `send-confirmed-outreach-touches` v13 at 2026-08-10 12:31Z):** the branded HTML wrapper stripped from outreach email (shared `_shared/outreachEmailBody.ts` replacing two byte-identical private copies), snapshot-over-template precedence fixed so admin edits in `TouchPreviewModal` actually send, and the possessive fix extended to the subject line. _Resend webhook unblocked at the gateway (`fix/resend-webhook`, 9 Aug 2026, no migrations, edge function code unchanged):_
- **The webhook was never going to work, for a reason the earlier diagnosis missed.** The 7 Aug entry in Section 11 attributed the zero-invocation state entirely to the unset `RESEND_WEBHOOK_SECRET` and the unregistered endpoint. Both were true, but there was a third fault underneath them: `resend-outreach-webhook` was deployed with **`verify_jwt = true`**, the only machine-called function in the project that was (the cron, the public enquiry endpoint and the output-file endpoint are all `false`). Resend sends svix headers and no Supabase JWT, so every event would have been rejected by the gateway with a 401 *before the handler ran* — the signature check, the secret, and the whole bounce/open pipeline behind it were unreachable. Fixing only the secret would have left the endpoint just as dead, with the same empty columns and the same silent logs.
- **Fixed by redeploying with `--no-verify-jwt` (v11 → v12).** The uploaded source is byte-identical to v11; this release carries the flag change and nothing else. Verified by POSTing to the endpoint with no `Authorization` header: it now returns the handler's own `{"error":"invalid_signature"}` (401), where before the gateway would have answered "Missing authorization header". That distinction is the proof the request reaches the function — and it confirms the handler is correctly **fail-closed** while `RESEND_WEBHOOK_SECRET` is unset, since `verifyResendSignature` returns false on an empty secret.
- **`supabase/config.toml` added** (the repo had none). It records `verify_jwt = false` for the five machine-called functions, so a future `supabase functions deploy` cannot silently reintroduce this. Functions absent from the file keep the CLI default of `true`, which is right for every admin/client endpoint.
- **The secret cannot be generated locally — this reverses the intended order of operations.** Resend's webhooks are Svix-backed; the signing secret is issued by Resend at endpoint-registration time as `whsec_<base64>`, and `verifyResendSignature` base64-decodes it to build the HMAC key. A locally generated random hex string would decode to the wrong bytes and 401 every event — indistinguishable from the current broken state, but now with a secret set, which is a worse place to debug from. So: register in Resend first, then copy the issued secret into Supabase.
- **No migration needed.** `outreach_touches` already has `opened_at`, `bounced_at` and `resend_message_id`; `suppression_list.email` is UNIQUE (the bounce path's `onConflict` upsert resolves); `leads.status` and `outreach_touches.status` permit `'bounced'` and `'cancelled'`. Next migration number stays `0093`.
- **Closed out 9 Aug 2026.** The endpoint is registered in Resend, `RESEND_WEBHOOK_SECRET` now holds the signing secret Resend issued (the orphaned July value is overwritten), and every handled event was verified live against the deployed function before Monday's batch.
- **How it was verified, without waiting on Resend's test event.** Once the real signing secret was in hand, valid svix signatures can be generated locally, so the whole matrix was exercised directly: a correctly signed request returns 200, a tampered signature returns 401, a replayed `email.opened` leaves the original `opened_at` untouched (first-occurrence idempotency), and `delivered_at`/`opened_at`/`clicked_at` all populate on a real touch. Results: a `Transient` bounce records `bounce_type` and changes nothing else, leaving the lead `active` with its pending touches intact; a `Permanent` bounce sets `bounced_at` on both touch and lead, writes `suppression_list.reason = 'hard_bounce'`, flips the lead to `'unsubscribed'` and cancels the future touch; a complaint does the same with reason `'complaint'` and **cancels a `held` touch**, which is the concrete proof that the `('scheduled','held')` correction mattered, because the spec's `('pending','scheduled')` would have left that touch live. All fixtures and the one real touch were reverted afterwards: 267 leads, 207 touches, 68 scheduled, and zero rows carrying any event data, matching the pre-test baseline exactly.

_Webhook widened to the full Resend event set (`fix/resend-webhook`, 9 Aug 2026, migration 0093):_
- **Three things in the original spec did not survive contact with the real APIs**, and each would have failed silently rather than loudly:
  - **`email.unsubscribed` is not a Resend event.** Resend's `email.*` events are sent, delivered, delivery_delayed, opened, clicked, bounced, complained, failed, received, scheduled and suppressed (verified against Resend's event-type list, Aug 2026). A handler branch for it would have been dead code that never fired, giving false confidence that unsubscribes were covered. They already are, by a different route: the portal's own `/unsubscribe/:token` page and the `unsubscribe_by_token` RPC from migration 0072.
  - **`leads.status = 'Suppressed'` would have thrown on every write.** `leads_status_check` permits only new, active, replied, meeting_booked, converted, not_interested, unsubscribed, bounced and archived. "Suppressed" is a *display label*, not a stored value: `LeadsTab.tsx:452` maps `{ val: 'unsubscribed', label: 'Suppressed' }`. The handler writes `'unsubscribed'`, which is what makes a suppressed lead appear under that filter chip.
  - **`status IN ('pending', 'scheduled')` would have matched half of what it should.** There is no `'pending'` touch status; `outreach_touches_status_check` allows scheduled, sent, skipped, cancelled, failed and held. The cancel path uses `('scheduled', 'held')`.
- **Hard and soft bounces are now separated, and only hard ones suppress.** Resend's payload carries `data.bounce.type` (`Permanent`, `Transient`, `Undetermined`) alongside `subType` and a human-readable `message`. Treating all bounces alike, which is what the old two-event handler did, burns a reachable lead over a full mailbox or a greylisting delay. `bounce_type` is recorded for every bounce including the ignored ones, so a soft bounce that was correctly skipped stays distinguishable from an event that never arrived.
- **A spam complaint is now its own severity.** It shares the suppression path with a hard bounce but logs at error level and writes `suppression_list.reason = 'complaint'`, which migration 0093 adds to the reason check constraint. A complaint harms deliverability for every future recipient, not just the one who reported it, so it should never be readable as an ordinary unsubscribe in the logs.
- **Failed database writes now return 500.** The handler previously ignored every write result and returned 200 regardless, so a failed update meant Resend never retried and the event was gone. This was already logged as debt in Section 11 and was cheap to close while rewriting the routing.
- **Migration 0093** adds `delivered_at`, `clicked_at`, `complained_at`, `unsubscribed_at` and `bounce_type` to `outreach_touches`; `bounced_at`, `complained_at` and `unsubscribed_at` to `leads`; `'complaint'` to the suppression reason constraint; and a partial index on `outreach_touches.resend_message_id`, which every event looks up and which had no index at all (only the primary key on `id`). _Admin shell sticky regression fixed (`fix/pagination-scroll`, 2 commits, no migrations, **merged to main 9 Aug 2026**):_
- **Reported as "the top nav, sidebar, page header and tab bar are all fixed, leaving no room for content". Measurement showed the exact opposite:** nothing was fixed except the pagination bar. At scrollY 800 on production, `TopBar` sat at top **-800** and the sidebar at **-744** — both scrolled entirely off screen, despite both being declared `position: sticky`. The page header and tab bar are `position: static` and scroll away by design. Confirmed shell-wide, not Outreach-specific: `/portal/admin/invoices` behaved identically (TopBar 0 → -168, sidebar 56 → -112).
- **Root cause:** `AdminShell`'s root set `overflow-x: hidden` (added by PR #13's admin mobile pass). Per the CSS overflow spec a `visible` value computes to **`auto`** when the other axis is `hidden`/`scroll`/`auto`, so this produced `overflow-y: auto` — measured directly on the live element. That made the shell root the nearest scrolling ancestor for every sticky descendant, but it is `min-height: 100vh` and grows with content rather than scrolling internally, so those descendants were sticking to a box that never moves.
- **Fix:** `overflow-x: clip`, which clips the same horizontal overflow without creating a scroll container, so `overflow-y` stays `visible`. Emitted as `.ec-admin-shell { overflow-x: hidden; overflow-x: clip; }` so a browser without `clip` support keeps today's behaviour instead of losing horizontal clipping entirely.
- **Verified by before/after on the real production DOM** (the preview requires a login this session could not perform): with the rule injected, at the same scrollY 800 `TopBar` returns to **0** and the sidebar to **56**, while the fixed pagination bar is unchanged and page horizontal scroll stays at 0. Mobile path exercised at a 570px viewport (below the 768 breakpoint): sidebar correctly absent, `TopBar` pinned through scroll, bar at left 0 and flush, zero horizontal scroll. The deployed preview bundle was separately confirmed to contain the rule with the fallback in the correct order.
- **Scope decision:** the request was to make the tab content its own scroll container, scoped to the three tab wrappers with `AdminShell` untouched. That was not buildable as scoped — the tab wrappers sit inside `OutreachAdmin`'s in-flow header and tab bar, so capping only their height yields two scrollbars, and pinning the tab bar or deriving heights from shell constants both require editing the excluded files. Raised with measurements and the smaller shell fix was chosen instead.
- **Both docs corrected:** they described `TopBar` as "sticky across every admin route", which had not been true in practice.

_Unified business-hours email scheduling + scheduled_for precision fix (migrations 0091-0092, merged to main 6 Aug 2026):_
- **The ask, verbatim:** emails should only go out inside the recipient's own local working hours, computed in this order — (1) resolve the recipient's local time by geography, (2) if before 9:30 AM local, hold for 9:30 AM local today, (3) if between 9:30 AM and 5:30 PM local, send now, (4) if past 5:30 PM local (or a weekend), hold for 9:30 AM local on the next business day. Before this, `send-outreach-email` and `confirm-scheduled-touch` each had their own separate, inconsistent logic — a 09:00-18:00 window in one, a hardcoded-to-ET-only `nextBusinessDay930ET()` in the other, neither matching the requested policy exactly.
- New shared module `supabase/functions/_shared/businessHours.ts` — single source of truth for both edge functions. Exports `COUNTRY_TZ` (10-country IANA map), `resolveTimezone()`, `zonedWallTimeToUtc()` (2-pass DST-safe convergence, no external date library — Deno's edge runtime has no built-in timezone-aware wall-clock converter), and `computeSendDecision(now, timeZone)` implementing the exact 4-step policy above. Both `send-outreach-email` (the direct "Send email" click) and `confirm-scheduled-touch` (the "Review in Advance" approval click) now call the same function and can never drift apart again.
- **Migration 0092 — the missing piece:** `outreach_touches.scheduled_for` had been a bare `date` column since migration 0072 (0076's `scheduled_for timestamptz` is a *different* table, `linkedin_posts` — verified before writing this). Every precise "9:30 AM recipient-local" instant `computeSendDecision()` produced was silently truncated to just a date the moment it was written — a `date` column has nowhere to put the hour — so the 5-minute cron's `scheduled_for <= now()` check was comparing against midnight, not the real target time. Converted to `timestamptz`; `resume_enrollment()` fixed in the same migration (`scheduled_for + v_days_paused` doesn't typecheck against `timestamptz + integer` — confirmed live via the exact Postgres error before writing the fix — replaced with `make_interval(days => v_days_paused)`). 6 TypeScript call sites across `AdminShell.tsx`, `OutreachAdmin.tsx`, `AdminDashboard.tsx`, and `TodayTab.tsx` updated from exact-date/`.lte` string comparisons to proper instant comparisons (`.lt` against tomorrow's start, or `new Date(...).getTime()` comparisons) — `LeadsTab.tsx` and the cron function needed no change, already comparing full instants.
- **Bug found live via a user screenshot** (a lead's "Scheduled" card showed a send time roughly 9 hours off from the current time): 10 real touches had `scheduled_for` corrupted to exactly midnight UTC. Root cause: they were approved via the new `confirm-scheduled-touch` logic *during the exact window* the column was still `date`-typed — the precise instant got truncated to a bare date at write time, then that already-truncated date was cast to midnight UTC when migration 0092 ran moments later. This was actively dangerous — the cron did not re-validate business hours before sending, only `scheduled_for <= now()`, and all 10 rows were roughly 2 minutes from becoming due when found. (**That is no longer true as of v14, 11 Aug 2026** — the cron now gates on the recipient's live local window, which would have caught these 10 independently of the `scheduled_for` corruption. Entry left standing as the historical record; see Section 1's 11 Aug entry.) Immediately pushed all 10 six hours out as a protective measure, then recomputed and set each one's correct value using its properly-resolved per-lead timezone once the second bug (below) was also fixed.
- **Second bug found in the same investigation:** `leads.country` stores inconsistent formats live — "United States", "US", "United Kingdom", "India" all present simultaneously across real rows — but `COUNTRY_TZ` only recognized 2-letter codes. Every full-name-country lead (the majority) silently fell through to the `America/New_York` default, meaning UK and India leads were being scheduled against US working hours with no error or warning. Fixed by adding a `COUNTRY_NAME_TO_CODE` lookup and rewriting `resolveTimezone()` to check both formats before falling back. `leads.country` itself is not yet normalized at entry — see Section 11.
- Both edge functions redeployed with the shared module (`confirm-scheduled-touch` v10, `send-outreach-email` v15). All 10 affected touches verified corrected in the database (9 US leads → next 9:30 AM ET, 1 India lead → next 9:30 AM IST), each with an explicit `recipient_timezone` now stamped so future runs skip country resolution entirely for those rows.
- **Not yet live-tested with a real send at the actual 9:30 AM window** — the fix, the data correction, and the redeploy are all confirmed correct by direct SQL/logic verification, but no one has watched a real approved touch actually leave the outbox at its computed local time yet. **Supabase secrets are write-only.** `supabase secrets list` returns names, SHA-256 digests and timestamps; there is no `get` or `reveal` subcommand and the Management API hashes the value too. ### Motion

`src/portal/motion.ts` exports the full nested scale as **`motionSystem`**
(`duration.fast`, `easing.enter`, `distance.md`, `delay.short`), including the
values `theme.ts` lacks: `micro`, `moderate`, `slower`, `expressive`, `snap`,
`emphasized`, distances and delays. **Nothing imports it yet, deliberately.**
`theme.ts` separately exports flat `motionTokens` (`durationFast`, `easeEnter`)
and that is what all ~60 current call sites use.

**The names differ on purpose.** Had both been called `motionTokens`, an import
from the wrong module would read `motionTokens.durationFast` as `undefined`,
which serializes into a CSS string as the literal text "undefined" and silently
kills the transition with no console error. `motionSystem` makes that
unreachable, and lets both be imported into one file during the migration.

Migrating the call sites is one atomic pass (MOTION_SYSTEM.md Phase 2), not
opportunistic work, and it must reconcile three real divergences: `durationSlow`
is 350ms in `theme.ts` against 360ms in the scale, `easeDefault` is a different
curve from `easing.standard`, and shimmer runs at 1.5s live against the 1.4s
originally specified (the code value won).

**Pagination does not animate on a page change, and that is settled.** A `tbody`
fade was proposed and rejected: the swap is a client-side array slice with
nothing to wait for, and COMPONENT_PATTERNS.md's Pagination Pattern already
decided that the bar holding still is what makes the content read as the thing
that changed. MOTION_SYSTEM.md reaffirms it rather than reopening it.

`prefers-reduced-motion` is handled once globally in `src/styles/index.css`
(added 9 Aug 2026, the first such handling anywhere in `src/`). That stylesheet
is app-wide, imported by `src/main.tsx`, so it covers the marketing site too.
There is no CSS file under `src/portal` at all, which is why it could not be
scoped to the portal.

**Signing secret rotation policy** (added 9 Aug 2026). Rotate `RESEND_WEBHOOK_SECRET` whenever a `whsec_` value has appeared anywhere it should not have: a chat transcript, a screenshot, a shared terminal, a commit that was later reverted. The procedure, in this order, because the two halves must match and Resend owns one of them:

1. Resend dashboard, the webhook, **Rotate signing secret**. Resend issues the new value. **It cannot be supplied**, so there is nothing to generate locally; a self-generated string would simply fail every signature check.
2. `supabase secrets set RESEND_WEBHOOK_SECRET=whsec_… --project-ref urrinqwcrpivmvenupiu`
3. Confirm via MCP `get_logs` (`service: edge-function`) that `resend-outreach-webhook` is not returning 401. A 401 after a rotation means the two halves disagree, which in practice means step 2 used the wrong value or has not propagated yet.
4. **Send a correctly signed request using the OLD secret and confirm it now returns 401.** Skipping this is the easy mistake: a valid-signature 200 and a tampered-signature 401 both pass whether or not the old secret was actually revoked, so neither proves the rotation landed. Only the old-secret rejection does.

Signatures can be generated locally once the secret is known, so none of this needs Resend's test event: sign `{svix-id}.{svix-timestamp}.{raw body}` with HMAC-SHA256 keyed on `base64decode(secret without the whsec_ prefix)` and send it as `svix-signature: v1,<base64>`. Use an `email_id` that matches no touch, so the probe verifies the signature path without writing anything.

There is a **gap between steps 1 and 2 during which every event 401s**, because Resend is already signing with the new secret while Supabase still holds the old one. Resend retries, so events are not lost, but do not rotate mid-batch if it can wait.

### Dev tooling

| Script | Command | Notes |
|---|---|---|
| `npm run dev` | `vite` | Dev server |
| `npm run build` | `vite build && node prerender.mjs` | Transpile only. esbuild strips types without checking them, so **the build cannot fail on a type error** |
| `npm run typecheck` | `tsc --noEmit` | Added 9 Aug 2026. Dev-only, **deliberately not wired into the build** |

`npm run typecheck` is the answer to the long-standing note that this repo had no `tsc` at all and that a browser pass was therefore the only real check on a refactor. It is advisory: it reports, it never blocks, and `npm run build` neither reads `tsconfig.json` nor fails on anything the typecheck finds.

Three configuration decisions in `tsconfig.json` are worth knowing before changing it:

- **`strict: false`.** This is the first time the codebase has been type checked. The first run should surface real breakage, not every implicit `any` across 238 files. Turning `strict` on is the natural follow-up once the current list is dealt with, and it will produce a much longer one.
- **`include: ["src"]` only.** `supabase/functions` is Deno: it imports from `jsr:` and `https:` specifiers and uses the `Deno` global, none of which resolve under a bundler config. Those 25 files are checked by Deno at deploy time, not here.
- **Not the `tsc --init` defaults.** The generated config uses `module: nodenext`, which demands explicit file extensions on relative imports and would report an error on nearly every import in the project. It is set to `bundler` to match Vite. `verbatimModuleSyntax`, `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` are also off for the same signal-over-noise reason. Note that TypeScript 7 **removed `baseUrl`** (TS5102); `paths` resolves relative to the config file instead.

`typescript`, `@types/react` and `@types/react-dom` are devDependencies. The React types were not optional: without them every `.tsx` file fails on JSX and the report is worthless.

**The three real defects, all resolved on `fix/ts-real-defects` (merged to `main` 9 August 2026, no migrations):**

- ~~`DesignSystemPage.tsx:613`~~ **Resolved.** The Foundation sub-nav was duplicated inside both branches of the render conditional, and the copy in the typography branch sat under a guard that had already narrowed `foundationSection` to `"typography"`, making its `"colors"` comparison statically false. Fixed by hoisting the sub-nav to a single render gated on `activeTab`. **The audit's "something is not rendering" was wrong:** the narrowed copy produced the correct inactive styling by accident, so nothing was visibly broken. What it actually removed was dead code and a duplicated block. Verified in the browser both ways, and the DOM now holds one sub-nav (2 buttons) instead of two.
- ~~`LightboxThumbnailStrip.tsx:144`~~ **Resolved.** Same shape, same conclusion, and **also behaviourally correct before the fix.** The `kind === 'image' ? 'other' : kind` guard sat in the else of a `kind === 'image'` ternary, so `kind` was already narrowed to exactly `NonImageThumbIcon`'s own union and the guard could never fire. Dropped it. Verified pdf, video and other each still resolve to their own icon, and an undefined `kind` still falls back to the image branch.
- ~~`DesignSystemsCaseStudy.tsx:878`~~ **Resolved, and this one was a genuine visual bug.** cva emits **no variant classes at all** for an unrecognised value (`defaultVariants` only fill in for `undefined`), so the button got base and size classes only. The call site sets `borderColor` inline but nothing set a border *width*, so the outline never painted and the button read as bare text on the dark CTA surface. Measured live: `border-top-width` was `0px` before, `1px` after. Fixed by moving the call site to `inverse`, the variant documented for an outlined button on a dark surface, rather than adding a seventh near-duplicate to the union.

**Two of the three were dead code, not broken rendering.** Only the `outline` variant changed what a user sees. A TS2367 says a comparison is statically false, which is not the same as saying the wrong branch ran; here two of them were redundant guards that happened to sit on the correct side.
